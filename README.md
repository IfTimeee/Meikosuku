# SillyTavern Compressed Save

> 纯前端扩展：拦截大体积 POST 请求，自动 gzip 压缩请求体。
> 专治跨境云酒馆「保存 18MB 卡 50 秒」。
>
> by 莓可莉丝（meikorisu）for iftime ฅ^•ﻌ•^ฅ
>
> v1.2.2 | MIT | gzip 压缩 + SaveGate 指纹去重 + 排队合并 + 全局串行

---

## 背景

SillyTavern 默认每次保存聊天时，都会把**整个聊天的完整 JSON** 通过 POST 发给后端。

聊天记录本质上是大量重复结构的纯文本（角色名、消息模板、HTML 标签、CSS 类名等），对 gzip 极为友好。但 SillyTavern 的前端并不会自动压缩请求体——于是当聊天累计到十几 MB 后，每次保存都要把十几 MB 原始 JSON 从国内上传到美国的 VPS。

更糟的是，SillyTavern 的保存触发点极多：刷新页面、进入聊天、发一条消息、重新 roll……短短一两分钟内能触发 **5~10 次全量上传**，其中大量请求的**内容完全相同**。在跨境高丢包线路上，多请求并发还会互相挤占带宽、触发重传风暴，把 12 秒能传完的数据拖成 80 秒。

典型场景：
- 跨境 VPS（香港/日本/美国）
- 国内家庭宽带上行普遍只有 2~5 Mbps
- 每发一条消息触发两次保存（发送前 + 生成后），外加各种 UI 状态变更的连带保存
- 一次 18MB 的上传耗时约 50 秒，叠加并发互踩就是"发一句话卡两分钟"

结果就是"发一句话卡两分钟"。

## 这个扩展做什么

### 第一层：gzip 压缩（v1.0 起）

1. **Hook `window.fetch`**：拦截 SillyTavern 发出的所有网络请求
2. **匹配目标请求**：只对 `/api/chats/save` 和 `/api/chats/group/save` 这类保存接口生效
3. **gzip 压缩请求体**：使用浏览器原生 `CompressionStream('gzip')` 即时压缩
4. **附加请求头**：设置 `Content-Encoding: gzip`，移除旧 `Content-Length`
5. **后端零改动**：Express 的 `body-parser` 默认 `inflate: true`，会自动解压，服务端完全无感知

### 第二层：SaveGate 智能滞留闸门（v1.2.0 起）

针对「短时间内疯狂重复保存」的酒馆特色，在压缩之前再加三道阀门：

| 阀门 | 机制 | 效果 |
|---|---|---|
| ① 指纹去重 | 对请求体计算 SHA-256 指纹，窗口期内（默认 300 秒，可配置）内容完全相同的请求**直接拦截**，0ms 返回伪造的 200 响应 | 相同内容绝不重复上传 |
| ② 排队合并 | 前一个请求还在传输时，新请求自动挂起排队并**覆盖旧排队**，前一个完成后只发送最新一份 | 并发请求收敛为一个 |
| ③ 全局串行 | 全局互斥锁，同一时刻全网**只允许一个上传在飞** | 避免 TCP 并发互踩导致丢包雪崩 |

**安全设计（绝不让"去重"变成"丢数据"）：**

- **只有服务器真实返回 200 OK，指纹才会被登记**。上传中途刷新页面、断网、超时——指纹绝不入库，下次保存必定真传。
- 指纹默认**不跨刷新保留**（`persistDedupe: false`）：刷新 = 状态可能变化，刷新后第一次保存一定真传。可选开启 localStorage 持久化换取更极致的省流。
- 排队中被覆盖的旧请求会收到合成的成功响应（数据已包含在最新那份里），不会让酒馆 UI 卡死。
- 面板提供 **⚡ 强制下次全量** 按钮（控制台 `CompressedSave.forceSave()`），随时清空指纹强制真传。

整个流程对 SillyTavern 前端透明，上层代码不知道请求被压缩过、被去重过。

## 效果

聊天 JSON 的 gzip 压缩比一般在 **8~12 倍**；叠加去重后，高频操作场景的实际流量再降一个量级。

实测数据（13MB 聊天 + 5.8MB 设置，跨境线路）：

| 指标 | v1.0（纯压缩） | v1.2.2（压缩 + SaveGate） |
|---|---|---|
| 单次上传（13MB → 3.7MB） | 4~11 秒 | 4~5 秒 |
| 短时间 16 次保存操作 | 16 次全量真传，总耗时上百秒 | **10 次真传 + 6 次指纹秒杀**，`failed: 0` |
| 相同内容重复上传 | 全部真传 | 全部 0ms 0 流量拦截 |
| 多请求并发 | 互相挤占带宽，单请求耗时膨胀 6 倍+ | 串行排队，窗口稳定跑满 |

## 安装

把整个文件夹放到 SillyTavern 的扩展目录中（二选一）：

**全局安装**（所有用户可见）：
```
SillyTavern/public/scripts/extensions/third-party/CompressedSave/
```

**用户级安装**（仅当前用户可见）：
```
SillyTavern/data/<your-user-handle>/extensions/CompressedSave/
```

安装后刷新 SillyTavern，打开「扩展面板」即可看到 **🐈 Compressed Save (猫猫加速喵~)**。

> 不需要运行 `npm install`，不需要修改任何配置文件。这是一个纯前端插件。

## 设置项

| 设置 | 默认值 | 说明 |
|---|---|---|
| 启用压缩 | ✅ 开 | 总开关 |
| 指纹去重 | ✅ 开 | SaveGate 阀门①：相同内容窗口期内直接拦截 |
| 全局串行 | ✅ 开 | SaveGate 阀门③：同一时刻只允许一个上传在飞 |
| 实时日志 | ✅ 开 | 面板实时日志表格开关 |
| 指纹有效期（秒） | 300 | 去重窗口时长，过期后相同内容会重新真传一次作保险 |
| 压缩阈值（字节） | 4096 | 小于此值的请求体不压缩（小请求压缩反而浪费 CPU） |
| 跨刷新保留指纹 | ❌ 关 | 开启后指纹写入 localStorage，刷新页面不重复上传（省流但有小概率风险，见安全设计） |
| 控制台详细日志 | ❌ 关 | 开启后在 F12 控制台打印每次压缩/去重/合并的详情 |
| 拦截路径 | `/api/chats/save`、`/api/chats/group/save`、`/api/settings/save` | 一行一个，支持路径子串匹配。可自行添加其他需要压缩的 API |

> 另有高级参数：上传超时熔断 `sendTimeoutSec`（默认 180 秒，超时自动 abort 释放通道），可在 F12 中通过 `CompressedSave.settings` 修改。

## 面板功能

扩展面板在 SillyTavern 扩展设置页内，展开后提供完整的可视化诊断，**无需开 F12**：

- **状态徽章**：绿色「已启用」/ 红色「已禁用」
- **统计卡片**：
  - 真实压缩 / **指纹去重** / **排队合并** / 跳过 / 失败次数
  - 最近一次压缩比
  - 累计上行流量节省（原始体积 → 压缩体积 → 节省百分比）
- **实时日志表格**：最近 30 条记录，包含时间、状态（`ok` / `dedupe` / `skip` / `error`）、路径、原始大小、压缩后大小、压缩比、gzip 耗时、总耗时、备注
- **⚡ 强制下次全量**：清空指纹缓存，下一次保存必定真实上传（逃生舱）
- **🧪 自检测速**：本地跑一次 1MB 假数据自检，验证 `CompressionStream` 与 SHA-256 可用性
- **📋 复制诊断**：将所有配置和统计打包为 JSON 复制到剪贴板，方便排查
- **🧹 清空统计**：重置所有计数器和日志（同时清空指纹）

## 兼容性

### 浏览器

需要原生支持 `CompressionStream` API：

| 浏览器 | 最低版本 |
|---|---|
| Chrome / Edge | 80+ |
| Firefox | 113+ |
| Safari | 16.4+ |

不支持时会自动跳过压缩（日志标记为 `skip`），不会报错。

### SillyTavern 后端

- Express `body-parser` 默认 `inflate: true`，开箱即用
- 如果后端配置了额外的反向代理（Nginx、Caddy 等），需确保代理不会对 `Content-Encoding: gzip` 的请求体的 Content-Length 做校验（通常不会）

### 出错绝不丢数据

设计哲学是：宁可多卡 50 秒，也绝不让保存失败。

- **压缩阶段**出错（如 `CompressionStream` 不可用）：自动回退原始未压缩请求，正常发送。
- **发送阶段**：请求一旦真实发出，任何后续错误都**不会再回退重发**（v1.2.2 修复），杜绝"压缩上传成功 + 原始全量重传一次"的双重写入灾难。
- **去重阶段**：指纹只在服务器真实响应 200 后登记，任何中途失败/中断都不会污染去重表。
- 上传超时（默认 180 秒）会通过 `AbortController` 真正中止连接，释放串行通道，不会卡死后续保存。

## 技术原理

### 拦截与闸门流程

```
SillyTavern 调用 fetch()
        │
        ▼
patchedFetch() — 扩展的 hook
        │
        ├── 条件不满足 ──► 透传给原始 fetch()（无影响）
        │
        └── 条件满足 ──► SHA-256(原始 body)
                            │
                            ▼
                    SaveGate.submit(path, hash, sender)
                            │
                            ├── 指纹命中且在窗口内 ──► 直接返回伪造 200（0ms 0流量）
                            │
                            ├── 同路径正在传输 ──► 排队覆盖，等前一个完成后只发最新一份
                            │
                            └── 全局串行锁空闲 ──► gzip(body) ──► 原始 fetch(compressed_body)
                                                        │
                                                        ▼
                                            Express body-parser 自动解压
                                                        │
                                                        ▼
                                            成功 ──► 登记指纹，放行后续排队任务
                                            失败 ──► 不登记指纹，下次必定真传
```
```

### gzip 为什么能压缩 8~12 倍

聊天 JSON 中存在大量重复字符串：
- 角色名（反复出现）
- `<div class="mes ...">` 等 HTML 结构
- CSS 类名 `mes_text`、`mes_block` 等
- JSON 键名 `name`、`mes`、`swipe_id` 等

gzip 的 LZ77 + Huffman 算法对这些重复模式极高效——字符越重复，比例越高。

### 小请求为什么跳过

低于 `minBytes`（默认 4KB）的请求不压缩。原因是：
- 极小的 payload 压缩后可能反而变大（gzip header 约 20 字节）
- 4KB 以下传输耗时已经很低，压缩节省的时间几乎为零

## 常见问题

**Q: 我从 Nginx 反代时开了 `gzip`，客户端还需要这个吗？**

Nginx 的 `gzip` 是压缩**响应体**（服务器→客户端），这个扩展压缩的是**请求体**（客户端→服务器）。两者方向不同，互不冲突。

**Q: 会影响非保存请求吗？**

不会。扩展只拦截 `targetPaths` 中列出的路径，且只处理 POST/PUT/PATCH，其他请求（聊天流、生成、配置读取等）全部透传。

**Q: 压缩会消耗多少 CPU？**

浏览器原生 `CompressionStream` 是底层 C++ 实现，不在 JS 主线程执行。1MB JSON 的 gzip 通常 <50ms，对前端无感知。

**Q: 我能压缩其他 API 吗？**

可以。在「拦截路径」中添加对应的路径关键字即可（如 `/api/settings/save`）。
